# Working on this repo

For any coding agent (Claude Code, Cursor, others). We're at a hackathon: move fast, but follow the spec.

1. Read `README.md`, `idea/overview.md` and `specs/README.md` first. If they disagree, the newest file wins.
2. **Capturing:** when asked to capture a meeting, thought or research, put it in the folder `README.md` names for it, with a dated file name. Keep people's words. Never invent facts, quotes or numbers. For a transcript, write a `-summary.md` beside it with: decisions, open questions, action items (who and what), and any spec changes they imply.
3. **Building:** read `specs/000-overview.md` first: it has the architecture, the contracts between lanes, and which folders each lane owns. Ask (or check the branch name) which lane you're in, and stay in that lane's folders. Exception: a step in your lane that lists **Allowed files** outside your folders (the Web help steps S.W1, G.W1, P.W1) lets you edit exactly those files and no others. Build against `packages/contracts`; when another lane's service isn't there yet, use a fake behind the same interface instead of waiting or building it yourself. Work on the first unticked step in your lane in `product/BUILD.md`, or the step you were asked for. Read every spec it names. Build what the spec says. Every acceptance criterion in scope gets a test whose name starts with its ID (`it("XX-1 ...")`). If something is ambiguous, pick the simplest reading, log it in `product/DECISIONS.md`, and keep going. Don't edit specs unless you were asked to.
4. **Done** means the tests pass, the box in `BUILD.md` is ticked, a line is added to the log at its bottom, and the work is committed with the step and criteria IDs in the message.
5. Work on your own branch, never `main`. Pull before starting and push when a step is done.
6. Never commit secrets (use `.env`, which is gitignored). This repo is public. Never deploy or create cloud resources unless a human asked you to.
7. Don't edit `meeting-recordings/` except to add new transcripts or summaries.
8. Changing a contract (types, routes, index names) means one PR that edits both `packages/contracts` and `specs/000-overview.md`. Say so in the PR title so the other lanes see it.
9. Gitar reviews every PR. Open the PR with auto-merge on (`gh pr create ...` then `gh pr merge --auto --merge`): it merges itself when `ci` is green, so nobody waits. Keep working; when Gitar comments, fix what it flags in a follow-up PR or answer it in the thread. If `ci` fails, comment `gitar auto-apply:on` on the PR and let Gitar fix it before fixing it by hand.
10. Telemetry: follow the conventions in 000. Never put names, LinkedIn text, notes or other personal text in spans, metrics or logs.
11. Every OpenAI call needs a deterministic fallback, and tests never call OpenAI, Dash0 or a remote Elasticsearch.
12. **Cluster and Radar.** We run on the hackathon's Radar vcluster (`conquest`, namespace `team-conquest`, URL `https://conquest.cnh.radarhq.io`). Read `deploy/README.md` before touching `deploy/`, `argocd/` or the cluster. Use Radar Cloud's MCP (`radar-cloud`) to observe and operate: call `list_clusters` once per session, take the id of the cluster named exactly `conquest`, and pass it as `cluster` on every call; never touch `cnh` or another team's cluster. Deploys are GitOps: a PR merged to `main` builds and deploys; don't apply or patch app manifests on the cluster. The Radar procedures are skills in `.agents/skills/` (`get-started`, `ship`, `debug-failure`, `canary-release`, `demo-story`).
13. **Real issues only.** Never break things on purpose. When something real breaks, investigate with Radar (and Dash0 Agent0) before fixing by hand, and save the evidence (`demo/evidence/`, `product/TOOLING.md`).
