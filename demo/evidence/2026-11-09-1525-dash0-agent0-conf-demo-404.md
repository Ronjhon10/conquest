# Dash0 Agent0: live site's join/map/boss pages 404 on `conf-demo` (2026-11-09 15:25 MT)

**How we found it.** While building the "Conquest live" dashboard (P.7), a PromQL query over `dash0.spans` showed 31 ERROR spans in `conquest-game-api` on the cluster (`deployment.environment.name = demo`) in one hour, even though the service catalog showed 0% errors. We asked Agent0 through the Dash0 MCP (`runTask`) to investigate. Thread: https://app.dash0.com/goto/agent0?thread_id=f46c2138-4894-4bd0-932b-df64ffb5892d

**What Agent0 found.**
- All 31 are Elasticsearch-client spans that got a 404.
- 26 of them (13 lookups, two spans each) come from browser requests to `GET /api/game/conferences/conf-demo`. All 13 returned 404 to the user.
- The other 5 are harmless first-boot index-exists checks.

Agent0 read the public repo and traced the cause:
- The web app hardcodes `conf-demo` in its join, map and boss links (`apps/web/src/components/landing.tsx`, `ui.tsx`).
- That ID exists only in the fake-API fixture (`packages/contracts/src/fixtures.ts`).
- game-api gives every real conference a random ID (`services/game-api/src/routes/conferences.ts`), so the lookup can never succeed.
- The page fetches the conference in a `Promise.all` with its other requests, so the whole page shows the error notice.

Agent0 also confirmed that search-api's errors and Elasticsearch's 2.6% error rate are only expected 404s: startup checks plus one inference-endpoint existence check.

**Why the dashboard missed it.** game-api's own request spans aren't marked ERROR on a 404. Only the Elasticsearch client spans are. The "Conquest live" dashboard therefore counts non-2xx responses per route, not just ERROR spans.

**Fix.** Web and Game lanes: point the links at a real conference ID, or create a `conf-demo` conference on the cluster. PR: _to be added_.
