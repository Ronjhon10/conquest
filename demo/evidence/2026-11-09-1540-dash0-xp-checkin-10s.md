# Dash0: boss check-ins take 10 seconds (2026-11-09 15:40 MT)

**How we found it.** The 2-bot smoke run of the new load script (`scripts/load`, P.8) against https://conquest.cnh.radarhq.io showed every game-api request at about 5 s and check-ins timing out at 10 s. Health checks and talk search stayed fast (0.1–0.5 s). Our Dash0 check rule **"Conquest XP award p95 over 300 ms"** (`observability/dash0/`, P.7) had already been **firing (critical) since 21:28 UTC**, observing a p95 of 10.4 s. Teammates' real check-ins at 21:28–21:29 took 10–20 s each.

**What the trace shows.** One `POST /api/game/xp` (trace `93388c04f5fca8a6640c0e05dc5c369b`), 10.4 s in total:
- Every Elasticsearch read and search took about 60 ms.
- Two `PUT conquest-attendees/_doc/<id>` writes took **4.0 s and 4.5 s**.
- The `conquest-xp-events` create took 0.35 s.

**Root cause.** `services/game-api/src/store/elastic.ts` writes with `refresh: "wait_for"`, so every write blocks until the index refreshes. On Elastic Serverless that takes several seconds. An XP award writes the attendee twice and the event once, so a check-in costs about 9–10 s. That's far over the spec's 300 ms XP SLO, and it would make the live demo feel broken.

**Fix (Game lane).** Don't wait for refresh on writes the response doesn't depend on. Reads by id are already real-time in Elasticsearch; only searches and aggregations (leaderboard) need a refresh. PR: _to be added_. After the fix, re-run `npm run load -w scripts/load` and save the before/after p95 here.

## Radar AI investigation (same window)

We ran Radar's AI investigation on Deployment `game-api` to rule the cluster in or out: https://app.radarhq.io/c/yka3x0NpFNY/investigations/chat_W4HEC5zR67xENZ9X

Verdict, 0.9 confidence: **game-api is healthy at the Kubernetes level.** No crash loop, no restarts, no failed pulls, and CPU around 0.008 cores, so the 10 s isn't the pod or the node. Radar did find the readiness blip: during the 21:33 rollout the new pod refused connections for about 10 s while starting. With a single replica, that is the 503 window we hit at 21:33. That part is fixed in PR #66 (2 replicas, `maxUnavailable: 0`, a `preStop` drain, PDBs).

**Together:** Radar cleared the infrastructure, Dash0's trace pinned the latency on the app's Elasticsearch writes, and the load test turned both up.
